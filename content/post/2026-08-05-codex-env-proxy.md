Codex 的这类网络故障很磨人，因为它很少表现为干脆断网。大部分时间任务还能跑，一到中途却会突然重连，浏览器操控偶尔也停在那里；更麻烦的是，手机端始终连不上 Mac 上的 Codex。起初我也以为只是 VPN 节点延迟太高，几种现象混在一起以后，这个判断听上去很合理。

排查时最有用的线索来自 Clash 的 TUN 开关。我把 TUN 打开，手机远控马上恢复，关掉以后连接随即中断，这一开一关已经足以说明，Codex 原先采用的网络路径有问题。可 TUN 从系统网络层接管的是整机流量，Chrome 原有的联网路径也会跟着变化，一些依赖浏览器插件型代理访问的特定站点，开启 TUN 后便无法继续按照原规则连接。

问题因此变得很具体。Codex 需要稳定走 Clash，Chrome 和其他软件仍要保留原来的配置。为了修一个应用，没有必要把整台电脑的网络重新安排一遍，最后我把改动收窄到一个 `.env` 文件，只让 Codex 明确连接 Clash 的本地代理端口。

我把它叫作 `.env` 定向代理法。Clash 继续使用原来的节点和分流规则，Chrome 继续使用原来的插件型代理，整机网络则不必长期交给 TUN。

## TUN 有效，只是管得太宽

TUN 适合处理那些完全不肯读取代理设置的程序。系统建立虚拟网卡以后，软件愿不愿意配合已经不重要，流量会从更靠下的位置被接走。如果电脑上只有一套代理规则，这种处理很省事；若 Chrome 里还有一套插件型代理，两个层级的规则碰到一起，结果就未必符合原来的预期。

`.env` 的作用要窄得多，它不碰系统路由，也不改 Chrome 设置，只把代理地址交给 Codex 启动时读取。Codex 收到地址后先连到 Clash 的本地端口，接下来的节点选择和分流仍由 Clash 处理，连接过程可以简单写成下面这样。

```text
Codex
  ↓ 读取代理环境变量
127.0.0.1:<CLASH_PORT>
  ↓ 交给 Clash 现有规则
OpenAI / ChatGPT / 手机远控相关服务
```

Chrome 不会读取 Codex 目录中的这份文件，因此仍按原有的插件型代理规则运行。不过这套方法主要用于关闭 TUN 的情况，如果整机 TUN 仍然开着，Codex 的 `.env` 并不能让 Chrome 绕开系统层的接管。

## 先确认端口，再放入文件

现成教程里的端口不能直接照抄，不同电脑上的 Clash 配置可能不同。端口一旦填错，Codex 会把请求送到没有服务监听的地址，结果通常比偶尔重连还干脆，直接完全连不上。可以先在 Clash 的设置或配置文件中找到 HTTP、Mixed Port 一类的本地代理端口，下文用 `<CLASH_PORT>` 代替真实数字，实际填写时要把它换成当前端口，尖括号也一并删掉。

接下来的操作只需要一个文件。

1. 使用 `Command + Q` 完全退出 Codex。
2. 用任意纯文本编辑器新建文件，文件名写成 `.env`，不要保存成 `.env.txt`。
3. 把下面的内容完整复制进去。

```dotenv
HTTP_PROXY=http://127.0.0.1:<CLASH_PORT>
HTTPS_PROXY=http://127.0.0.1:<CLASH_PORT>
ALL_PROXY=http://127.0.0.1:<CLASH_PORT>
NO_PROXY=localhost,127.0.0.1,::1

http_proxy=http://127.0.0.1:<CLASH_PORT>
https_proxy=http://127.0.0.1:<CLASH_PORT>
all_proxy=http://127.0.0.1:<CLASH_PORT>
no_proxy=localhost,127.0.0.1,::1
```

把所有 `<CLASH_PORT>` 换成刚才确认的端口，再将文件放到 `~/.codex/.env`。如果需要在 Finder 中定位这个目录，可以按 `Command + Shift + G`，输入 `~/.codex` 后直接前往；由于 `.env` 属于隐藏文件，看不到时再按 `Command + Shift + .` 显示隐藏文件。文件放好以后重新启动 Codex，不需要额外开启什么，也不用再改 Clash 配置。

## 大写和小写为什么都要留

文件里的两套变量看着有些重复，留下它们是为了兼容不同的网络库。有的组件读取 `HTTP_PROXY`，有的更习惯 `http_proxy`，大小写都写可以减少主程序已经走代理，某个后台服务却仍在直连的情况。

其中，`HTTP_PROXY` 和 `HTTPS_PROXY` 负责常见的网页请求，`ALL_PROXY` 供支持通用代理变量的连接使用。`NO_PROXY` 则留给本机通信，Codex 的部分组件会访问 `localhost`、`127.0.0.1` 和 `::1`，这些地址没有必要再绕进 Clash，否则本机进程之间的通信反而会多走一圈。

Codex 需要完全退出再启动，也和这里有关。环境变量通常在进程启动时读取，只关闭窗口却保留后台进程，旧的网络设置很可能还在继续使用。

## 日志给出的答案更可靠

配置完成后，我先检查了进程连接和前后日志。Codex 的 Electron 网络进程与后台服务都连上了 Clash 的本地监听端口，随后由 Clash 按照原有规则，把 OpenAI、ChatGPT 和手机远控相关流量送往既定节点。改动只发生在 Codex 怎样找到 Clash 这一段，Clash 内部已经配置好的分流并没有被重写。

前后的日志差别很明显。配置前的一个 Codex 实例，在大约 15 分钟内出现了 50 条 `net::ERR_*` 网络错误；配置后的观察窗口约为 9 分钟，`reconnectAttempt > 0` 和 `net::ERR_*` 都是 0，此前依赖 TUN 才能连接的手机远控，在 TUN 关闭后也能用了。

这些结果足以证明改动有效，但我不愿意把它写成永久根治。测试期间仍出现过一次启动阶段的统计请求超时，代理出口做了 40 次探测，其中一次在 5 秒内发生 TLS 超时；多数成功请求用了 0.8～1.6 秒，少数升到 2～3.7 秒。Clash 节点本身依然存在延迟波动，`.env` 处理的是 Codex 经常走到错误的直连路径，节点质量不会因为多了一个文件就改变。

## 浏览器操控还要单独看

Codex 主连接稳定以后，浏览器操控仍有可能卡住。为了分清这两个问题，我又单独测试了内置浏览器和 Chrome 操控。本地页面上的点击、输入、下拉选择、前进后退和 DOM 读取都能正常完成，说明浏览器操控能力可以工作；访问外部网页时，仍出现过页面已经加载，控制调用却长时间等待的情况，日志里也见到过内置浏览器会话路由不可用，以及 Chrome 扩展或 CDP 桥接超时。

`.env` 主要处理 Codex 到代理出口的连接，内置浏览器还要依赖浏览器会话，Chrome 操控还要依赖扩展、标签页认领和 CDP 通信。整体网络变稳以后，浏览器控制可能跟着改善，但不能因此认定所有卡顿都会消失，排查时仍要把这些环节分开看。

## 不满意就把文件拿走

这套方法的回滚也很轻。先用 `Command + Q` 完全退出 Codex，再把 `.env` 从 `~/.codex/` 文件夹移到别处，确定以后不会再用也可以直接删除；重新启动 Codex 后，这份定向代理配置便不再生效。

如果之后想恢复，把保留的 `.env` 放回原处，再完全重启 Codex 即可。这个过程不会修改 Clash 规则、macOS 系统代理、Chrome 插件型代理或其他软件的设置。若 `~/.codex/.env` 原本就存在，则应先复制一份到其他位置保存，避免覆盖掉原文件中的其他配置。

同样的思路也能用于其他软件，前提是软件愿意读取代理环境变量，或者明确支持从某个 `.env` 文件加载配置。`~/.codex/.env` 是 Codex 使用的位置，其他应用通常不会来这里找文件，因此换到别的软件时，还要先确认它认识哪些变量、从哪里读取配置，以及改完以后是否需要完全重启。

在这次测试中，TUN 关闭后手机远控恢复可用，Codex 主连接的错误明显减少，Chrome 也保留了原来的插件规则。如果以后的软件升级让这份配置失效，把文件移出原目录，网络便会回到改动前的状态。
